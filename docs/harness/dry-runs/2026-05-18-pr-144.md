## 判定 (verdict: adopt)

**Case A 採用、Case B 破棄**。判定根拠:

1. **仕様 1-8 を全カバー**: Case A は本セッションで実証された仕様 1-8 (cmux サブコマンド辞典 / 1 ペイン=1 PR / 30s ポーリング / 自動回答 / stale display / 60% handover / R-15 代行 merge / ファイル経由 prompt 送信) を即運用可能な粒度で記載。Case B は frontmatter + 一般論のみで、A3 で本格化前提だが、orchestrator は **A2 follow-up として今すぐ運用する** ことが目的のため skeleton は不適合。
2. **教訓 10 系統が具体例化されている**: Case A の Gotchas 13 件は全て PR# / 観測事象 / 対象コマンドを引用、本セッション実観測の知見が即適用可能。Case B の抽象論では同種事故 (重複 prompt 送信 / stale 誤解釈 / 思考動詞辞書未登録 / cwd 喪失干渉 / 長文 prompt 欠落 等) を予防できない。
3. **100-point rubric スコア差**: Case A 97 vs Case B 95、特に「description trigger 明示」「Gotchas 具体性」「単独テスト可能性」で差。
4. **dry-run 必須条件への適合**: 「Skill 新規追加」は dry-run 必須 + adopt 判定で commit + push に進む条件 (`.claude/rules/harness-meta-criteria.md` §dry-run 必須条件)。Case A が改善基準 (誤検知減 / 規約遵守率向上 / 提案精度向上) を全て満たすため adopt。
5. **配置先一致**: Case A は `.claude/skills/orchestrator/SKILL.md` に配置、Case B は配置せず本 dry-run ファイルにのみ比較材料として記録。
