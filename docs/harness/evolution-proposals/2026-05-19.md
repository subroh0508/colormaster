# 概要 (5 行以内)

harness-meta / harness-evolution が起票する改修 PR (Skill / rule / template 変更) に対し、
変更前後 dry-run の結果から **改善度 / 再現性 / 副作用** の 3 軸を定量スコア化する評価フレームを導入する。
既存 dry-run template は verdict 3 値 (adopt / discard / escalate) のみで定量根拠が不在、特に
副作用と再現性の検出が verdict 判定に寄与していない。本提案で評価軸 / 計測手順 / 閾値 / PR description
必須記載フォーマットを SoT 化し、レビュワーが定量根拠でハーネス進化 PR を Approve 可能化する。

## 3 軸の定量定義 (本提案で SoT 化、rule / template に反映)

| 軸 | 計測対象 | 計測手順 | 閾値 (推奨初期値、運用熟成で調整) |
|---|---|---|---|
| **改善度** (Improvement Score) | 旧版で発生していた Problem の再発率 | 1) 対象 Skill / rule の関連 retrospective (直近 N 件、推奨 5-10 件) の `⚠️ Problem` セクションから関連 Problem を抽出 (M 件)。2) M 件のシナリオを新版 dry-run subagent (適用版) に投入。3) 再発した件数 / M 件 = Problem 再発率 (%)。 | **Problem 再発率 ≤ 30%** (= 改善率 ≥ 70%) で「改善あり」判定。0% (完全解消) が理想だが Skill の本質的限界もあるため 30% を許容ライン |
| **再現性** (Reproducibility Score) | 同一手順 / 同一引数 / 同一プロンプトでの新版出力の安定性 | 1) **「dry-run 入力記録仕様」 4 ブロック (起動コマンド / Subagent プロンプト全文 / 実行環境 / 入力ファイル) を固定** した上で、新版 dry-run subagent に同一入力を **N=10 以上 (推奨初期値、Anthropic 公式の「20-50 simple tasks」推奨を coding agent 規模に圧縮した値)** 投入。コスト制約で N=5 採用時は **信頼区間が広い旨を verdict コメント必須化**。 2) 各実行の重要セクションを「measurement target × メトリクス対応表」(下記参照) に従い分類: set / scalar / categorical / 自由文 のそれぞれに **Jaccard / 変動係数 / 完全一致率 / LLM-as-judge** を適用。 3) 各メトリクスの **calibration 由来の閾値** で安定判定。 | **閾値は固定値ではなく calibration 由来** (Braintrust「fixed numeric values 非推奨」準拠): N=20 baseline 計測 → **median - 1σ** を初期閾値、N=10 以上で再計測したい場合は moving average で更新。**初期 placeholder**: Jaccard ≥ 0.80 / CV ≤ 0.15 / 完全一致率 ≥ 70% / LLM-as-judge ≥ 0.80。**入力記録が不在 / 不完全 (4 ブロック欠落) の場合は再現性スコア算出を見送り** (9 通り指針 §9 で人間判定要扱い) |
| **副作用** (Side-Effect Score) | 旧版で問題なく動作していたシナリオの退化 / 新規違反検出 | 1) 旧版が正常出力していた **基準シナリオ集 (= golden set、初期 K=5、下記「基準シナリオ集更新フロー」に従い iterative 拡張、Evidently / Anthropic 公式の「start small and keep adding」準拠)** を保持。2) 新版 dry-run subagent に K 件を投入。3) 各シナリオを **「改善 / 変化なし / 退化」** の 3 値で判定 (`改善`=新版が明らかに良化 / `変化なし`=出力 diff なしまたは無視できる差 / `退化`=旧版より明らかに劣化、誤検知増 / 規約違反検出 / Critical findings 増)、退化件数 + 新規 Critical 件数を集計。 | **閾値型基準** (Evidently「lte = 0.1 / 10% acceptable fail rate」準拠、zero-tolerance は LLM flakiness で全件 escalate 倒れするため非採用): **退化率 ≤ 20% (= 退化件数 / K)** + **新規 Critical findings ≤ 1 件** で「副作用なし」判定。退化率 > 20% または Critical ≥ 2 件は guardrail 違反 (Braintrust の「unintended side effects」概念) として変更を reject 候補。閾値は基準シナリオ集サイズ K に応じて運用熟成で調整 |

### measurement target × メトリクス対応表 (再現性軸の本格化、本提案で SoT 化)

再現性軸の「重要セクション」は データ型ごとに別メトリクスを適用する (Jaccard 統一は set 比較限定で適切、scalar / categorical / 自由文には不適合)。

| measurement target | データ型 | 推奨メトリクス | 算出方法 | 初期閾値 (calibration 前 placeholder) |
|---|---|---|---|---|
| 該当規約 ID 列挙 (例: R-13 / R-15) / 改修対象ファイルリスト / Skill 名集合 | set of strings | **Jaccard 係数** | `|A ∩ B| / |A ∪ B|`、N 回試行のペアワイズ平均 | 平均 ≥ 0.80 |
| Gotchas 数 / fix loop 回数 / 該当行数 等の数値 | scalar (integer / float) | **変動係数 (CV)** | `標準偏差 / 平均値` | CV ≤ 0.15 |
| verdict 後継ラベル (将来用途) / category 選択 | categorical | **完全一致率 (modal agreement)** | 最頻値の出現率 / N | ≥ 70% |
| 自由文 (SKILL.md 本文 / レビューコメント本文 / 説明文) | text | **LLM-as-judge semantic equivalence** | 別 subagent に「N 回出力の semantic 一致度」を 0-1 で判定 | ≥ 0.80 |

**Calibration 推奨手順** (運用熟成段階、Plan Phase 2 以降):

1. 既存 Skill (harness-meta / harness-evolution) の安定状態で N=20 baseline 計測を実施
2. 各メトリクスの **median - 1σ** を初期閾値の調整値とする
3. 3 PR サイクル分の dry-run 実績で moving average 更新

### 基準シナリオ集 (golden set) 更新フロー (副作用軸の本格化、本提案で SoT 化)

**基準シナリオ集** = 旧版で正常動作する既知シナリオ K 件を固定保持したテストセット (LLM eval 業界で *golden set / golden dataset* と呼ばれるもの)。新版に同じ K 件を投入して退化検出に使う。

初期サイズは **K=5 件** で開始し (Anthropic 公式「20-50 simple tasks」を Skill 改修向けに圧縮)、以下の場面で **iterative 追加・更新**:

1. **新規 retro の `⚠️ Problem` 発生時**: pr-retrospective Skill が生成する learning ファイルの Problem セクションから「副作用候補」(例: 「旧版で動いていたが新版で誤動作」型) を自動抽出 → 基準シナリオ集の追加候補に
2. **harness-meta の `📝 harness-meta フィードバック` `保留` 表に「副作用懸念」理由で新規追加された場合**: 自動的に基準シナリオ集の候補化
3. **orchestrator 手動追加**: subroh0508 が「これは恒久的に検証すべき」と判断した場合
4. **古い基準シナリオの除外 (retire)**: 3 PR サイクル連続で 改善 / 変化なし のみ (退化発生ゼロ) かつ対象 Skill / rule が廃止された場合は基準シナリオ集から除外可

更新 PR は `harness/golden-set-update-YYYY-MM-DD` ブランチで起票 (ブランチ名は branch-naming.md の英語規約に従い `golden-set` を採用)、本 SoT に従い基準シナリオ集ファイル (`docs/harness/dry-runs/golden-set.md`、本提案で同時新規追加、`harness-meta-criteria.md` の関連 docs としてリンク。ファイル名は docs-structure.md のパス命名規約で英語維持) を編集。

**Plan 実装フェーズで決定が必要な open question**:

- 基準シナリオ集のサイズ上限 (Anthropic 推奨上限 50 件をそのまま採用するか、Skill 改修向けに 15-20 件で打ち止めとするか) → Plan Phase 1 で計測コスト試算後に判定
