- `.claude/skills/dependency-upgrade/SKILL.md` Phase 2 §changelog 解析 を新規 subsection で詳細化:
  - **Step 1 (上流公式 changelog 取得)**: `gh release view --repo <upstream-repo> <version>` で取得、失敗時は Step 2 へ
  - **Step 2 (GitHub Releases API 取得)**: `gh api repos/<upstream-repo>/releases/tags/<version>` で取得、rate limit 配慮 (4000 req/h)、失敗時は Step 3 へ
  - **Step 3 (Renovate PR description parse)**: PR body の `## Release Notes` セクションを Markdown parser (Renovate 既定形式) で抽出、失敗時は Step 4 へ
  - **Step 4 (commit history 走査)**: `gh api repos/<upstream-repo>/compare/<old-tag>...<new-tag>` で commit list 取得、depth 上限 50 commits
  - **失敗時のフォールバック**: 全 step 失敗時は「changelog 取得不能、人間確認必須」コメントを `gh pr comment` で post し、Plan / Epic 起票を保留

### Try #2: SemVer major bump 検出ロジックを Phase 4 内 sub-procedure として SoT 化 (PR 個別観点、priority: high、Problem #2 直接対応)

- `.claude/skills/dependency-upgrade/SKILL.md` Phase 4 §SemVer major bump 検出 を新規 subsection で詳細化:
  - **Step 1 (Renovate PR title 確認)**: PR title が `chore(deps): update <package> to v<major>.<minor>.<patch>` 形式で、`<major>` が変化 → major bump
  - **Step 2 (libs.versions.toml diff 走査)**: `gh pr diff` で `gradle/libs.versions.toml` の version 値 diff を parse、SemVer major 部分が増加 → major bump
  - **Step 3 (KMP プラットフォーム別判定)**: `kotlin.target.<platform>` 別に依存が分岐する場合、最大 bump 値を採用 (例: jvm が major bump、wasmJs が minor bump → major として扱う)

  - **1.x.x → 2.0.0 以降**: 標準 major bump 扱い (Epic 起票)
- 採用判定基準 2 (process improvement、SemVer major bump 検出ロジック詳細化) 該当
